How the Moana tide file is made

A step-by-step guide to make_tides.py. It takes the TPXO global tide model and turns it into the tide forcing file (TIDENAME) that ROMS reads. For every step we say what the code does and why it needs to, with figures made from the real Moana files.

Background

The idea: a tide is a sum of simple waves

The Moon and the Sun pull on the ocean with a few fixed rhythms. The biggest one, called M2, repeats every 12.42 hours (the Moon passes overhead about twice a day). Others repeat every 12 hours (S2, the Sun), about every 24 hours (K1, O1), and so on. Each rhythm is called a tidal constituent.

The period of each constituent is the same everywhere on Earth, because it comes from astronomy. Two things change from place to place:

  • Amplitude: how high the wave is at that place (in metres for sea level, m/s for current).
  • Phase: when the high water of that wave arrives, given as an angle from 0° to 360°.

If you know the amplitude and phase of each constituent at a point, you can rebuild the tide there at any time by adding the waves together:

ζ(t) = Σk fk Ak cos(ωk t − φk) ζ is sea level, A is amplitude, ω is the angular speed (2π / period), φ is the phase, f is a small correction for the year (step 3). The sum is over the 15 constituents.

TPXO (here TPXO9-atlas-v5, from Oregon State University) is a global tide model that has already worked out the amplitude and phase of each constituent, for sea level and for currents, on a 1/30° grid (about 3 km). ROMS cannot read TPXO as it is. It needs the same information on its own grid, with phases measured from its own clock, and with currents written as ellipses. make_tides.py does that translation. It is a Python version of the MATLAB OTPS scripts in Code-Commons (process_tides_GOG.m → otps2frc_v7.m), with pyTMD in place of t_tide and xarray in place of the OTPS program extract_HC.

One more idea before the steps. TPXO does not store amplitude and phase directly. It stores each constituent as a complex number, a real part and an imaginary part (hRe + i·hIm), where amplitude = |Re + i·Im| and phase = −angle(Re + i·Im). The script keeps the numbers in this complex form until the very end. The reason is that phase is an angle, and angles are hard to average. Halfway between 350° and 10° is 0°, but a plain average gives 180°. Complex numbers do not have this problem, so interpolation and corrections are safe in complex form.

1

Read the ROMS grid

scripts/make_tides.py:31–36 
grid = xr.open_dataset(GRID)
water = grid.mask_rho.values == 1
lon = xr.DataArray(grid.lon_rho.values % 360, dims=("eta_rho", "xi_rho"))
lat = xr.DataArray(grid.lat_rho.values, dims=("eta_rho", "xi_rho"))
h = xr.DataArray(grid.h.values, dims=("eta_rho", "xi_rho"))
What
  • Opens the ROMS grid file moana_grid_N50.nc.
  • Keeps the water mask, the longitude and latitude of every rho point, and the ROMS depth h.
  • Writes longitudes in the 0–360° form (% 360), so 179°W becomes 181°.
Why

The rho points are where ROMS wants the tide values. The mask is used at the end to set land to zero. h is needed to turn TPXO transport into current (step 2).

The Moana domain crosses the 180° line (it runs to 185°E). The TPXO cut runs from 160° to 186°, so ROMS points east of 180° must also be written as 180°–186°. If not, they would fall outside the TPXO box. The current grid file already uses 0–360°, so here % 360 is only a safety step.

2

Move the TPXO harmonics onto the ROMS grid

scripts/make_tides.py:38–53 
tpxo = xr.open_dataset(TPXO).sel(con=CONSTITUENTS)

def harmonics(var, scale=1.0):
    hc = (tpxo[var + "Re"] + 1j * tpxo[var + "Im"]) * scale
    i, j = distance_transform_edt(np.isnan(hc[0]), return_distances=False, return_indices=True)
    hc = hc.copy(data=hc.values[:, i, j])     # each land cell takes its nearest water cell
    return hc.interp(lon=lon, lat=lat).drop_vars(["lon", "lat"])

z = harmonics("h")
u, v = harmonics("u", tpxo.dep) / h, harmonics("v", tpxo.dep) / h

2a. Pick the constituents and make complex numbers

What

Selects the 15 constituents in CONSTITUENTS and joins each Re/Im pair into one complex number.

Why

We use all 15 that TPXO gives (the MATLAB version used 12). Complex form makes the interpolation below safe for phase, as explained above.

2b. Fill TPXO land with the nearest TPXO water

What

distance_transform_edt finds, for every TPXO land cell, the closest TPXO water cell. The land cell then takes that value. This is done for all constituents at once, with the land mask of the first one.

Why

The TPXO coastline and the ROMS coastline are not the same. Bilinear interpolation uses the 4 TPXO cells around a point, and one missing cell makes the result missing (NaN). In Moana, 354 of the 174,292 ROMS water points (0.2%) have at least one TPXO land cell among their 4. After the fill, all of them get a real value. (The MATLAB version filled only the boundary rows.)

2c. Bilinear interpolation to the ROMS points

What

hc.interp(lon=lon, lat=lat) takes the 4 TPXO cells around each ROMS rho point and makes a distance-weighted mean.

Why

TPXO is on a 1/30° (about 3 km) grid and ROMS is on a 5 km grid, so their points do not match (left panel above). TPXO is finer than ROMS and changes smoothly in the open ocean, so a simple bilinear step is enough.

2d. Currents from TPXO transport and ROMS depth

What

TPXO velocity is TPXO transport divided by the TPXO depth. The script multiplies it back by tpxo.dep to get transport (m²/s), interpolates the transport, then divides by the ROMS depth h.

Why

The two models do not have the same sea floor. South of Stewart Island the TPXO depth is 7 to 16 m, but ROMS h is 130 to 160 m. A thin layer of water carrying the same transport must move very fast. With transport ÷ ROMS h, ROMS moves the same volume of water as TPXO, but spreads it over its own depth.

Status. "Currents = TPXO transport / ROMS h" is a proposed choice (see docs/devlog.md). The MATLAB version used the TPXO velocity as it is. On the open edges of the domain, TPXO depth / ROMS h is 0.69 to 2.04.

3

Set the tide clock: nodal corrections and phase zero

scripts/make_tides.py:55–64 
names = [c.lower() for c in CONSTITUENTS]
_, _, V = pyTMD.constituents.arguments(mjd(REF_DATE), names)
nodal_u, f, _ = pyTMD.constituents.arguments(mjd(NODAL_DATE), names)
correction = xr.DataArray(f[0] * np.exp(1j * (np.radians(V[0]) + nodal_u[0])), dims="con")
z, u, v = z * correction, u * correction, v * correction

This is the step that most needs explaining. TPXO phases are not tied to a date. They are measured against the position of the Moon and the Sun (a "Greenwich phase"). ROMS has no astronomy in it. It only knows "time since TIME_REF + TIDE_START" and computes cos(ωt − φ) from there. So the script must work out what each wave looked like at that start moment. It does two things:

V at REF_DATE · phase zero

V is the astronomical angle of each constituent at REF_DATE (2026-01-01, the model start). Adding it to the TPXO phase turns "phase against the Moon and Sun" into "phase against the clock time REF_DATE". This is the time ROMS calls t = 0.

f and u at NODAL_DATE · 18.6-year cycle

The plane of the Moon's orbit turns round once every 18.6 years. This makes lunar tides a little bigger in some years and smaller in others. f scales the amplitude and u shifts the phase. Solar tides such as S2 have f = 1 and u = 0.

corrected = TPXO × f · ei(V + u) amplitude becomes f × A, phase becomes φ − (V + u)
Why one NODAL_DATE

ROMS keeps f and u fixed for the whole run. They change slowly (figure above), so we take them at the middle of the 3-month run (2026-02-15). Over 30 days the error from this is 1 to 3 mm (pyTMD test, Ross Sea grid).

Why V at REF_DATE, not NODAL_DATE

V moves fast: for M2 it goes round 360° every 12.42 hours. ROMS adds that movement itself through ωt. So V is needed only at t = 0, which is REF_DATE. If REF_DATE is not the ROMS start of tide time, every phase is wrong.

The same correction is applied to sea level and to both current parts, because they all belong to the same constituent and keep the same clock.

4

Turn u and v into current ellipses

scripts/make_tides.py:66–67 
Cmax, Cmin, Cangle, Cphase = pyTMD.ellipse.ellipse(u.values, v.values)
What

For each constituent and each point, pyTMD converts the complex east (u) and north (v) currents into the 4 numbers that describe a tidal ellipse.

  • Cmax: the fastest current in one cycle (semi-major axis) [m/s]
  • Cmin: the slowest current, at right angles to Cmax (semi-minor axis). Its sign gives the direction of rotation.
  • Cangle: the direction of Cmax, degrees from east
  • Cphase: when Cmax happens, as a phase angle
Why

Over one tidal period, the current at a point does not only go back and forth. It turns, and the tip of the current arrow draws an ellipse. This is the format that the ROMS tide file uses (the same as the MATLAB otps2frc_v7.m output). ROMS turns the ellipse back into u and v itself.

5

Set land to zero and write the ROMS file

scripts/make_tides.py:69–100 
def field(values, long_name, units):
    return xr.DataArray(np.where(water, values, 0.0), dims=dims, attrs={...})

"tide_Eamp":   field(np.abs(z.values), ...)
"tide_Ephase": field(np.degrees(-np.angle(z.values)) % 360, ...)
...
out.to_netcdf(OUT, encoding={"tidal_constituents": {"dtype": "S1"}})
What
  • Sea-level amplitude = |z|, phase = −angle(z) in degrees, 0 to 360. This is where the complex numbers end.
  • Every field is set to 0 on ROMS land.
  • tide_period in hours, from pyTMD's frequency of each constituent.
  • zero_phase_date = REF_DATE written as 20260101.
  • Constituent names are written as character arrays.
  • lon_rho, lat_rho, mask_rho and a history note are added.
Why

ROMS does not use tide values on land, but a NaN in an input file can still break the run, so land gets 0. The names, units and layout match the ROMS tide file convention and the MATLAB output, so ROMS reads the file without changes. The S1 character type is the netCDF form that Fortran reads for strings. The grid variables and the history note let anyone plot or trace the file later.

Downstream

How ROMS uses the file

In Apps/moana/Include/moana.h, SSH_TIDES and UV_TIDES are on and RAMP_TIDES is off. ROMS reads the file named by TIDENAME. At every time step it adds up the constituents with the formula at the top of this page, and builds the tidal sea level and the tidal currents from the ellipses. It adds these to the open-boundary values, so the tide comes into the domain through the edges.

The time t in that sum is counted from TIME_REF + TIDE_START. That is why step 3 must use the same date.
